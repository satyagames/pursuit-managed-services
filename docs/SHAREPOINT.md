# SharePoint: the lists, the settings, Setup and deployment

Everything the app needs from SharePoint, and what this project learned about it on the real site (PCOE). The three pages run from one folder of a
document library, in the signed-in browser, and talk to the same site's REST API (`/_api`) with the person's own sign-in: no server, no app
registration, no certificate, no Graph, nothing from a CDN.

- Every column of every list, its type, index, limits, purpose and who reads and writes it: **[SHAREPOINT-LISTS.md](../SHAREPOINT-LISTS.md)**, generated
  from the schema file (`npm run build:lists-reference`; `npm run docs:lists` fails when it is stale). The pages name that file in their messages.
- The steps for a deployer, with the real addresses: the release package's `RUNBOOK.md` (made by `npm run package:release`).
- How the old site was set up (other list names, `p_cec_01`, the legacy pages): [history/SHAREPOINT-DEPLOYMENT.md](history/SHAREPOINT-DEPLOYMENT.md) and
  [history/PROVISIONING.md](history/PROVISIONING.md), kept as the record.

## The lists at a glance

**Schema version 3.** Twelve lists and one picture library. The titles below have no prefix (`"listPrefix": ""`); a copy of the app with a prefix
(`"listPrefix": "Test"`) uses `TestPMSClients` and so on. The key is the code's name for a list and never changes.

**The rules every list keeps** (each is checked by Setup's Check Lists):

- `AppId` is the app's own id of an item, never SharePoint's numeric ID: single line of text, required, indexed, unique. A duplicate is how the app
  knows something exists already (one item per visit, one session per client and day).
- Every column the schema names must exist with exactly that internal name and type; no column but `AppId` is required to hold a value.
- An index on exactly the columns the app filters on (`indexed` in the schema). A filter on a column with no index fails once a list passes 5,000 items.
- Words from a fixed set are single lines of text, not Choice columns. Dates show **Date & Time** (a date-only column can read back as the day before).
  Yes/No columns default to No. A single line of text holds 255 characters; the app refuses a longer one before sending it.
- JSON (ordered id lists, a client's theme, a person's answers) is multiple lines of **plain** text, append-only off: rich text would corrupt it.
- **A client's theme** (`PMSClients.ThemeJson`): `{ version, primary, accent, plate?, tokens, assets: { hero, logo, background, backgroundFocus?, tile }, copy: {
  eventTitle, eventSubtitle, welcomeLine, logoText }, sample?, motion? }`. `motion` (Phase 15) is the client's Animations switch, `{ "enabled": false }` when it
  is off; absent, damaged or anything but `false` means on, and an older page ignores it. Turning it on or off changes nothing else, not `ThemeVersion`.
- An order is `SortOrder`: SharePoint keeps `Order` for itself.
- **The version.** The item `default` of PMSAppSettings carries `SchemaVersion`. Setup writes it, last, when the check is clean; every page reads it
  with that item, which it reads first anyway. Missing: `PMS-LST-010`; lower: `PMS-LST-011` (run Setup); higher: `PMS-LST-012` (upload newer pages).

## Who may do what

The table, list by list, is in [SHAREPOINT-LISTS.md](../SHAREPOINT-LISTS.md#permissions) and in the package's RUNBOOK.md (both made from
`scripts/permissions.js`, which reads who reads and writes each list from the schema). In short:

- **Participant accounts** (the iPads, and anyone who opens the participant page) need Contribute on PMSClientSessions, PMSParticipants,
  PMSGuestQRCodes, PMSVisitLog and PMSParticipantAnswers, Read on the rest and on PMSClientImages, and **no access at all to PMSAdminUsers**.
- **Facilitators** (the admin page) need Contribute on the content lists and the library, and on PMSVisitLog (Phase 16: Delete session removes a
  session's visit log), and Read on PMSAdminUsers.
- **Delete session** (Results, Phase 16) deletes items in six lists, which needs Contribute (it includes deleting) on each: PMSParticipantAnswers,
  PMSVisitLog, PMSParticipants, PMSGuestList, PMSGuestQRCodes and PMSClientSessions. An account refused in one (403) is told which list, in words; what
  came before it in that order is gone, the rest and the session item stay, and the session stays on Results to be deleted again once the right is
  given. The app changes no list's permissions.
- **What a delete leaves on the site: nothing, as seen on PCOE (19 Oct 2026, Satyadev).** The app sends SharePoint's item DELETE
  (`X-HTTP-Method: DELETE`), not the `recycle()` call. After a Delete session on PCOE, neither the site's Recycle bin (Site contents, Recycle bin) nor
  its second-stage recycle bin held any item of the session: the delete is permanent, as the warning says. The app has nothing to restore an item.
- **Setup** is run by a site owner (Full Control): it creates lists and columns, writes the version, adds admins and uploads the sample pictures.
- **PMSAdminUsers holds the facilitators' PIN hashes** (unsalted SHA-256) and the whole list reaches the admin page, so its permission is the real lock:
  break its inheritance and remove every group the participant accounts are in. The PIN gates the admin page's screens; it is not authorization.
- Permissions are per list, not per session or person: an account that may edit PMSParticipantAnswers can edit anyone's answers by calling REST
  directly. Lock the iPads (Guided Access, or a managed kiosk profile) so that no address can be typed.

## The settings file: `pms-config.txt`

Each page reads `pms-config.txt` from its own folder before anything else (once per load, never cached, 8 seconds at most). Its content is JSON:

```json
{"configVersion": 1, "listPrefix": "", "label": "PMS"}
```

| Setting | What it is | If left out |
|---|---|---|
| `configVersion` | Must be `1`. | `1` |
| `listPrefix` | What goes in front of every list title. A letter and up to 15 letters or digits, or `""` (no prefix, said on purpose). | **The page stops** (`PMS-CFG-001`), unless a build put one in. |
| `lists` | A title for one list that does not follow the prefix, by key: `{ "qrtokens": "GuestCodes" }`. | every list follows the prefix |
| `logoLibrary` | The picture library's title. | `<prefix>PMSClientImages` |
| `siteUrl` | The site, when the page's address would not give it (a sub-site): https, no trailing slash, and the page must be inside it. | from the page's address |
| `batch` | `false` when the site refuses `$batch`. | `true` |
| `support` | `{ "name": "...", "contact": "..." }`: who to ask, shown with a problem. | "Whoever published the app" |
| `label` | A short name for this copy (40 characters), shown in the admin bar and on Setup. | none |

A key that is not in this table, or a value that breaks its rule, stops the page by name: it is never ignored. **Why `.txt` and not `.json`:** PCOE
will not serve a `.json` file from a document library: it answers with its own "File Not Found" page, with status 200 (14 Oct 2026). The pages ask for
`pms-config.txt` and for nothing else; a `pms-config.json` in the folder is never read. To check a folder, open `<folder>/pms-config.txt` in a browser:
it must show the text.

Where each setting comes from: the file, then a value built into the pages (`PMS_` variables on `npm run build:svelte:release`, see
[TESTING.md](TESTING.md)), then, for the site alone, the page's own address. There is no default list prefix: a page that cannot tell which lists are its
own stops. A missing file (HTTP 404) is "no file"; any other failure (no connection, a time-out, a web page in the file's place, text that is not
JSON) stops the page with `PMS-CFG-002`, because falling through on an error is how a page ends up on another copy's lists.

| Code | Meaning | What to do |
|---|---|---|
| `PMS-CFG-001` | Nothing names this copy's lists. | Put `pms-config.txt` in the folder. |
| `PMS-CFG-002` | The file is there, or may be, and could not be used. Details: `unreachable`, `status <n>`, `page 200` (a web page came back: the sign-in page, or "File Not Found"), `json 200`, or `invalid <setting>`. | Fix the connection, the sign-in or the file; Try again. |
| `PMS-CFG-003` | Part of a page asked for data before the page knew its settings: a fault in the app. | Reload; send the Details to the developer. |
| `PMS-CFG-004` | The settings name another site than the one the page was opened from. | Open it from its own site, or remove `siteUrl`. |
| `PMS-LST-010`, `011`, `012` | The lists are not set up, older, or newer (see the version above). | Run Setup, or upload the newer pages. |

## Setup (`setup.html`)

Setup opens even when the others stop, and says the problem in full. Its steps, in order:

1. **This copy of the app**: what the pages use and where each value came from (the file, the build, the address): site, lists, picture library,
   batching, support, label, and the build name (`pms-<commit>`). Below it, **Where the lists are** asks SharePoint for each list by title (reads only).
2. **Lists.**
   - **Show the plan** reads the site (one read of its lists, one of each existing list's columns) and lists what is missing: lists, the library,
     columns with type, index and uniqueness, list settings. It also lists what it **will not touch**, each with its fix (a wrong type, rich text, a
     date shown date-only, a wrong internal name, a required column the app does not fill, a retired column). It writes nothing.
   - **Create** does exactly that plan and only adds: lists, then columns, then indexes and uniqueness, then settings, paced. It never deletes, renames
     or changes a column's type. It reads back every column and stops, naming it, if SharePoint made something else. A 403 stops it with "Your account
     cannot create lists on this site. A site owner must press Create, or create the lists by hand from SHAREPOINT-LISTS.md." Pressed again, it
     carries on from where it stopped.
   - **Check Lists**: every list and column, strictly, read-only.
   - **Mark the site as ready** writes the version (a new item, or `SchemaVersion` on an item without one; raises version 1 or 2 to 3), only when the
     check is clean and the library is there. A clean Create runs it by itself.
3. **Admins**: a name and a PIN of 6 to 12 digits, typed twice, stored only as the hash the admin page compares. There is no demo PIN on a new site.
4. **Sample clients** (optional): Kroger and Domino's with their activities, their six pictures uploaded to the library first. Run twice, it makes nothing.
5. **SharePoint self-test** (optional, a test site; safe on a new site): 11 steps, each with its request count. Create a participant item; update it with
   one write; read it back by `TrackId`; a second create with the same `AppId` is refused; list the session in one query; two reads in one `$batch`;
   delete everything it made; and four read-only probes that only report: which Yes/No filter spelling the site accepts, the longest `$filter` it
   answers, which columns a read that names none leaves out, and which columns it will not return by name. PCOE passed 11 of 11 (16 Oct 2026).

Then **Moving content made on another copy** (the seed-file import from `npm run export:sharepoint`; it never brings admins). After setup, delete
`setup.html` from the folder or restrict it to site owners: it can make lists and add admins.

## What SharePoint does, as this project found it

Each of these is handled in the data layer (`migration/src/lib/data/`) and modelled by the mocked SharePoint (`scripts/sharepoint-fake.js`) and the local
PCOE stand-in ([LOCAL-SITE.md](LOCAL-SITE.md)), so a test fails if the handling goes.

| What happens | Seen on | How the app handles it |
|---|---|---|
| A second item with the same unique `AppId` is refused with **HTTP 500** and words about duplicate values (not the documented 400). | PCOE, 14 Oct 2026 | A refusal with 400, 409 or 500 whose code or words say "duplicate" or "unique value" is treated as 409, "there already". |
| An item read that names no columns **leaves `ClientId` out** of PMSActivities items. | PCOE, 14 Oct 2026 | Every item read names its columns (`$select`, from `selectOf` in the schema); `scripts/test-named-reads.js` holds it. |
| A read that names a column called **`DisplayName`** is refused ("Value does not fall within the expected range"): every list item has a property of that name. | PCOE, 15 Oct 2026 | Schema version 3 renamed the two columns (`GuestName`, `SignedInName`); no column may be named like a list-item property (`scripts/test-schema.js`). |
| A `.json` file in a document library comes back as "File Not Found", **status 200**. | PCOE, 14 Oct 2026 | The settings file is `pms-config.txt`. |
| A read returns **100 items and a `__next` link** unless it asks for more. | SharePoint's documented paging | Reads ask `$top` and follow `__next` to the end. |
| `$batch` carries several reads in one request; some sites or engines refuse it. | Playwright's WebKit drops the `boundary=` of a batch response | Writes are never batched. A refused batch turns batching off for the page and reads one by one; `"batch": false` never asks. |
| A write needs a **request digest** (write token) from `/contextinfo`, which expires: an expired one is refused with 403 "The security validation for this page is invalid". | SharePoint's documented behaviour | The token is fetched once and kept; on that 403 it is fetched again and the write tried once more. |
| **Throttling**: 429 (and 503) with `Retry-After`. | SharePoint's limits | Waited out up to three times when the wait is 30 seconds or less; timers obey `Retry-After` for 15 minutes at most and back off to 5 minutes. |
| **PMSAdminUsers** is readable by owners and facilitators only (403 for others, in a `$batch` part too). | PCOE, by its owner's choice | The admin page says the account may not open it. |
| A query string over **2,048 characters** is refused. | ASSUMED (ASP.NET's default; not measured on PCOE) | Reads group ids 20 to a request (15 for session ids), which keeps them under 1,700 characters; the longest, Results' read of names for 20 sessions, is about 1,872 on the PCOE address (known, left open). |
| A sign-in page comes back where JSON was expected (an expired sign-in). | Any site | Said in words: "Your sign-in has expired. Reload this page to sign in again."; answers not yet saved are kept in the tab. |
| A column deleted by hand after the site was marked ready. | Mock only | The page stops with SharePoint's words naming the column; Check Lists names it. |

## Deploying a package

1. **Make it**: `npm run package:release` on a clean, committed tree. It builds in a fresh checkout of the commit, into
   `build-svelte/package/pms-<commit>/` and a zip: the three pages, `pms-config.txt`, `THIRD-PARTY-NOTICES.txt`, `RELEASE-NOTES.md`, `RUNBOOK.md` and
   `SHA256SUMS.txt`. It stops if a page holds a site address, a folder name, a PIN hash, the demo PIN or an old folder name, and checks the checksums
   in the folder and in a fresh unzip.
2. **Check the checksums** where you unzip it: `shasum -a 256 -c SHA256SUMS.txt` (macOS), or in PowerShell
   `Get-FileHash -Algorithm SHA256 index.html,admin.html,setup.html,pms-config.txt` and compare each with its line. Any mismatch: stop.
3. **Try it on a test folder first** (a folder of its own, with a `pms-config.txt` whose `listPrefix` names test lists, or the same lists if you accept
   that Go live there changes the live session for everyone).
4. **Upload** `index.html`, `admin.html`, `setup.html` and `pms-config.txt` to the folder, with those names, no sub-folder. Uploading over the old files
   replaces them; reload open tabs (Ctrl+F5).
5. **Follow RUNBOOK.md**: on a new site every step; on PCOE (lists of version 3), its note: replace the three pages and check the build name on Setup.
6. **Printed QR codes** carry the folder's address: moving the files means printing every code again.

**Rolling back.** Keep the previous package. Every package of schema version 3 (since `pms-da9fc8d`) works with the same lists, so going back is
uploading the previous package's three pages over the new ones; nothing in the lists changes. A package of an older version would stop with
`PMS-LST-012` on lists of version 3: do not go back past a version change. Answers saved meanwhile stay in the lists either way.

**When something fails**, send a screenshot with the **Details** line of any code, and the browser console's text. RUNBOOK.md says what each code means;
the table above says what SharePoint does that the app expects.
